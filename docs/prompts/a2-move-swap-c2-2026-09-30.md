## Item 2 (FIRST) — the swap must complete in ≤ 2 s, or apply-and-validate-after with Undo

**Observed:** MATH Mon 07:30 → Swap → click FIL Mon 06:00 gives
`ATLAS could not check this swap in time. Nothing changed.` The bound fires because the swap check is
too slow on live data.

**Where:** `commitRegularSwapNow` (`atlas-client/src/hooks/useTimetableMutations.ts:2243`) does **one
`POST …/manual-edits/swap/preview` then one `POST …/manual-edits/swap`**, with an 8 s bound
(`SWAP_COMMIT_BOUND_MS`). Server side: `previewManualSwapEntries` in
`atlas-server/src/services/manual-edit.service.ts` (route `manual-edit.router.ts:281`).

**Required outcome:**
1. **Diagnose first, with evidence.** Establish *which* request is slow and *why*: the preview's
   candidate loop over a live-sized run, an N+1 read, a missing index, an unbounded validation per
   candidate, or a request that never returns. Report the measured latency of each POST and the
   cause. Do not guess — instrument or time it against a realistic run shape.
2. **Make the operator's swap complete within 2 s.** Either:
   - (a) make the check fast enough (fix the server-side cause, or drop the separate preview and
     commit directly, letting the server validate), **or**
   - (b) **apply the swap and validate after**, with the receipt and Undo already on screen — the
     operator must never wait on a check to see their own swap land.
   Choose (a) or (b), say which, and name the measured before/after latency.
3. The bound stays as a backstop, but it must no longer be the thing the operator hits on ordinary
   live data. A swap that genuinely cannot be done still says so in plain words, in ≤ 2 s.
4. Receipt + Undo unchanged (item 1 of the previous cycle): the ONE receipt from
   `timetable-edit-receipt.ts`, contextual Undo, no review dialog on the one-action path.

**Failing-first:** a control that reproduces the too-slow path (a preview whose candidate work is the
live shape, or a mocked slow preview) and asserts the operator's swap still lands with a receipt and
Undo inside 2 s. It must fail on `d707051e`.

## Item 3 (SECOND) — `Remove from draft` must be IN the selected-class menu

**Observed:** on live the selected-class menu is
`Dismiss selection · Choose a new time · Change room · Swap with another class · Lock this class ·
View class details · Change Teaching Load owner · Teacher leaving · Expert details` — no
`Remove from draft`.

**Where:** that menu is `atlas-client/src/components/timetable/ScheduleReviewWorkspaceSelectedActions.tsx`
(rendered from `ScheduleReviewWorkspace.tsx`). The previous cycle added the row there but gated it on a
resolved **pre-generation draft placement** (`selectedDraftPlacementId`), so on a generated run
(Run 355) it is hidden — that is why the operator cannot see it.

**Required outcome:**
1. `Remove from draft` **appears in this menu for the class on screen** in the live walk's state
   (a generated run, Term 1, a normal selected class) — not only for a pre-generation draft
   placement. Decide and state what "remove from draft" means for a run entry (take the class out of
   the current draft/run and return it to the unplaced list) and use the capability that already
   exists for it; if the only existing capability is the pre-generation `DELETE
   …/pre-generation-drafts/{id}`, say so and wire the run-entry removal through the correct
   existing path — do not invent an endpoint.
2. **One action, no confirm dialog** (decision 11), receipt naming the class and that it went back to
   the unplaced list, and a contextual **Undo** that reverses it.
3. Do not show the row when there is nothing it can act on, and do not offer it for a published run.

**Failing-first:** a rendered control that mounts the real menu with the live-walk selection shape and
asserts `Remove from draft` is present and acts in one action with receipt + Undo. It must fail on
`d707051e`.

## Item 1 (THIRD) — a MOVE must say "Moved", a SWAP must name both classes

**Observed:** a move passes but the receipt reads `Swapped Luna from Mon 6:00 to Tue 6:00` — the verb
is `Swapped` for a MOVE.

**Where:** the one-action swap composer `composeSwapReceipt`
(`atlas-client/src/hooks/useTimetableMutations.ts:2126`) always composes `SWAP_ENTRIES`, and
`commitRegularSwapOneAction` (`useScheduleReviewWorkspaceState.ts:1193`, called at `:1295`, `:2058`,
`:2212`) routes the occupied-slot move/drop through it. `timetable-edit-receipt.ts` already maps
`MOVE_ENTRY → 'Moved'` and `SWAP_ENTRIES → 'Swapped'` (`:76`, `:81`) — the verb table is right; the
call site passes the wrong edit type.

**Required outcome:**
1. The receipt's verb must match the edit the server actually committed. When the committed result is
   a **move** (one class relocated), the sentence says `Moved …`. When it is a genuine **exchange**
   (two classes trade), it says `Swapped …` **and names both classes** — a sentence that names one
   class and says "Swapped" is not honest either way.
2. Derive the verb from the committed record, not from the client's intent — the same rule the rest of
   `timetable-edit-receipt.ts` already follows (`buildEditReceipt` takes the edit type and the
   committed delta).
3. Undo and the rest of the receipt are unchanged.

**Failing-first:** a rendered assertion that a committed move produces `Moved` (never `Swapped`) and
that a committed exchange names both classes. It must fail on `d707051e`.

   item must say so rather than printing a wrong term.

**Failing-first:** a rendered assertion that five same-section/subject/teacher rows with different
terms/sessions produce five distinguishable labels. It must fail on `d707051e`.
